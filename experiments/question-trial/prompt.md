# 問いの生成プロンプト（試行用・たたき台）

企画メモ `portfolio-plan.md` の 6.3「問いと想起学習」の方針を、そのまま指示に起こしたもの。
【追加】と付けた行は企画メモに書かれておらず、試行のために足した条件。採否は評価のときに決める。

---

あなたは、技術資料を読む人のために「読む前に提示し、読了直後と数日後にも同じ形で出題する問い」を作る。
入力は、資料の種類・言語と、読む範囲の本文（プレーンテキスト）である。本文に書かれていることだけを根拠にし、あなた自身の知識で補わない。

## 問いの方針

1. 用語の名前や設定値を答えさせる問いは作らない。
2. 次のどれかの観点で問う。観点は `angle` に記録する。
   - `why`：なぜその仕組みになっているのか
   - `condition`：条件が変わると何が起きるか
   - `compare`：別の方式と比べて何を得て何を失うか
3. 読む範囲の中心となる仕組み、理由、成立条件に絞る。細部は問わない。
4. 問いは原則2問以上。増やすのは、中心となる仕組みや理由が複数ある場合だけにする。細部を問うて数を増やさない。根拠のある問いが2問に足りなければ、無理に埋めずに `not_generated` に理由を書く。
5. 抽出されていない数式や図表がないと答えられない問いは作らない。本文中の `[図]`、`[図: …]`、`[数式]` は、中身が抜き出せなかった箇所を表す。
6. 仕様上の保証を問う場合は対象バージョンを、論文の結果を問う場合は実験条件や前提を、問いの文に含める。
7. 【追加】問いは数日後に資料が手元にない状態でも出題される。問いの文だけを読んで、どの技術の何についての問いかが分かるようにする。「この記事では」「上の図で」のような、資料を見ていないと意味が通らない書き方をしない。
8. 【追加】問いの文に答えを含めない。読む前に見せても、答えの手がかりにならないようにする。

## 模範解答の方針

9. 模範解答は2〜3個の要点に分ける。要点は1つにつき1文で、短く書く。詳しい説明は元の資料に任せる。
10. 要点は本文の言い回しをなぞらず、自分の言葉で書く。
11. 【追加】要点どうしは独立にする。「どの要点を言えたか」を1つずつ判定できるようにするため、同じ内容の言い換えを並べない。

## 根拠

12. 問いごとに、根拠となる箇所を本文から抜き出して `evidence` に記録する。
    - `quote` は本文と一字一句同じにする。言い換え、翻訳、省略（…）、語順の入れ替えをしない。
    - 【追加】1つの `quote` は本文の1つの段落（1行）の中に収める。改行をまたがない。長さは日本語で40〜200字、英語で1〜2文を目安にする。
    - `heading` には、その箇所がある直近の見出しを、本文の表記のまま（先頭の `#` は除いて）書く。見出しより前にある箇所は空文字にする。
    - `supports` には、その箇所で説明できる要点の番号（1始まり）を書く。
13. すべての要点が、少なくとも1つの根拠で説明できるようにする。根拠で説明できない要点は書かない。

## 言語

14. 問いと要点は日本語で書く。資料が英語でも同じ。`quote` と `heading` は原文のまま。

## 出力

次の形の JSON だけを出力する。

```json
{
  "material_id": "01",
  "questions": [
    {
      "id": "01-Q1",
      "angle": "why",
      "question": "問いの文",
      "key_points": ["要点1", "要点2"],
      "evidence": [
        { "quote": "本文から抜き出した箇所", "heading": "見出し", "supports": [1, 2] }
      ]
    }
  ],
  "not_generated": [
    { "topic": "作らなかった、または捨てた問いの題材", "reason": "理由" }
  ],
  "self_report": {
    "unit_fit": "この読む範囲は問いを作るのに適切だったか（長すぎる、中心が複数ある、など）を1〜2文で",
    "difficulties": "生成で迷った点や、方針のどれかを守りにくかった点を1〜2文で"
  }
}
```
