# S-002 実際の資料7本で問いの生成を試す

バックログ S-002 の試行の記録。企画メモ 6.3 の方針で問いと模範解答の要点を生成し、根拠の引用が本文に実在するかを機械的に照合した。実施日は 2026-11-16。

問いの質の評価は [evaluation.md](evaluation.md) にある。01・02 は自分で読んで判断し、問いごとの詳しい評価は Codex に任せた。

## 誰が何をしたか

S-002 は「自分で書く」の札が付いたストーリーだが、今回は次の範囲を Claude Code（Claude Fable 5.2）と Codex に任せた。

| 作業 | 担当 |
|---|---|
| 資料7本の選定 | Claude |
| 本文の取得と抽出（`tools/fetch.mjs`） | Claude |
| 生成プロンプト（`prompt.md`）。企画メモ 6.3 を指示に起こし、4行を追加 | Claude |
| 問いと要点の生成（資料ごとに独立したサブエージェント、各1回） | Claude |
| 根拠の引用の機械照合（`tools/report.mjs`） | Claude |
| 01・02 を読んで、問いが内容に合っているかを判断する | 自分 |
| 01〜05 の問いごとの詳しい評価 | Codex |
| 方針とプロンプトの採否（evaluation.md の「全体の所見」） | 自分 |

## 機械照合の結果

集計は [results/summary.md](results/summary.md)。

- 問いは7本で30問。1資料あたり3〜5問
- 根拠の引用93件は、すべて本文と一字一句一致した。記録された見出しも、引用がある位置の見出しとすべて一致した
- 要点は30問すべてが2〜3個（3個が27問、2個が3問）
- 観点の内訳は、なぜ12問、比べると9問、条件が変わると9問
- 生成側が「作らなかった」と申告した題材は26件。理由は、用語や設定値の問いになる、細部にあたる、本文に理由が書かれていない、のいずれか

照合が確かめているのは、引用の文字列が本文にあることと、引用のある見出しが合っていることだけである。要点がその引用から説明できるかは確かめていない。

## 本文の取得で分かったこと

S-005 の見積もりの材料。資料ごとの詳細は `results/` の各ファイルの「本文の取得」にある。

- 7本とも HTML の取得と本文の抽出に成功した。資料ごとに手を入れたのは、論文の読む範囲の指定だけだった
- 図の中身は1枚も残らない。alt だけが残り、DevelopersIO の記事（図17枚）では alt が「スクリーンショット 日時」で内容が分からない
- 表は残るものと落ちるものがある。論文の Table 1 は Readability が本体を落とし、キャプションだけが残った。論文の4章はこの表に依存している
- 数式は、そのままテキスト化すると崩れる。arXiv の HTML 版は math 要素の alttext 属性に LaTeX があり、これを取り出して対応した（3〜4章を含むページ全体で116個）
- 見出しの付け方はサイトごとに違う。Qiita の記事は h3〜h5 だけで書かれ、PostgreSQL のドキュメントは見出しの末尾に「#」が付き、ページの題は本文から落ちる
- 登録した URL と取得した URL が一致しないことがある。Builders' Library の URL は別ホストの別 URL に転送された。重複の判定には転送後の URL か canonical が要る
- 対象バージョンは本文から取れない。PostgreSQL は URL の `/17/` にしかなく、日本語の記事3本と Kleppmann の記事は対象バージョンを本文に書いていない
- 本文の前後に余計なものが残る。参考文献の一覧、メール購読の案内、公開日の行など
- Zenn の記事は段落の中で改行して書かれていて（HTML では br 要素）、抽出後の1行が短い
- Windows 版の curl（Schannel）は3サイトでエラー43になった。Node の fetch では7本とも取得できた。本番の Go の実装には関係しないが、手元で確かめるときに引っかかる

## 生成で分かったこと

数えられる事実と、生成した LLM の自己申告に限って書く。問いが良いかどうかの判断は含めていない。

- 1資料あたりの問いが3〜5問になった。企画メモの「原則2問以上」に対して多い。7本すべてで、生成側が「読む範囲に中心が複数ある」と申告し、01・06・07 では範囲を分けたほうがよいと申告している。1日の復習の上限（3〜5問）と突き合わせると、1資料で1日分を使う
- 30問のうち11問が「また、」「あわせて」で2つのことを問う形になっている。問いの文は67〜158字
- 対象バージョンを問いに含める方針は、本文にバージョンがない4本（01〜04）で守れなかった。04 は公開年と著者名で代用している。07 は、URL から読み取ったバージョンを人が生成側に伝えた
- 根拠を「1行に収める」という追加条件は、段落内で改行する 01 で引用を29〜73字の断片にした。01 は4問に対して引用が17件ある
- 英語の資料は1文が長く、引用が長くなった。07 は最大474字、06 は最大353字で、目安の「1〜2文」を守っても200字を超える。企画メモ9章の「資料の内容を再現しない」との兼ね合いを決める必要がある
- 追加した方針7（問いの文だけで何の問いか分かる）と方針8（問いに答えを含めない）がぶつかると、04・05・06 の生成側が申告している
- 図や表が落ちた箇所は、生成側が問いにするのを避けた（03 の trace の画面、06 の Table 1）。06 は表に頼らず、本文の文で言い切れる範囲で比較の問いを作っている
- 02 は元の記事に説明の食い違いがあり、生成側は食い違いのない場合に問いを絞ったうえで、誤記を含む文をそのまま引用したと申告している

## この試行の限界

- 生成は Claude Code のサブエージェントで行った。本文をファイルから読める状態で書いているので、API を1回呼ぶ本番の形とは条件が違う。使うモデルを変えれば、引用の一致率は下がりうる
- 生成は各資料1回で、同じ資料で結果がどれだけぶれるかは見ていない
- 資料は Claude が選んだ。自分が読みたい資料、読んだことのある資料ではない
- 抽出した本文はリポジトリに入れていない（`.cache/`）。記録したのは URL、取得日時、読む範囲の SHA-256、根拠の引用である

## 受け入れ条件との対応

| 受け入れ条件 | 状態 |
|---|---|
| 日本語と英語を合わせて5本の記事で、問いと要点を生成した結果が記録されている | 済み（記事5本と、論文1本、公式ドキュメント1本） |
| 用語や設定値を答えさせる問いが混ざっていないか、観点で問えているかを記事ごとに評価している | 済み（記事5本。[evaluation.md](evaluation.md)）。論文と公式ドキュメントの2本は、最小コアを技術記事に絞ったため評価していない |
| 要点が2〜3個に分かれているか、根拠を本文から抜き出せたかの所見が残っている | 済み（数は上のとおり。所見は [evaluation.md](evaluation.md) の記事ごとの欄と「全体の所見」） |
| 記事ごとに本文をどう取得したか、どこで手間取ったかがメモされている | 済み（`results/` の各ファイルと上の節） |

## やり直し方

```
cd tools
npm install
node fetch.mjs        # materials.json の資料を取得して .cache/ に本文を置く
# prompt.md と .cache/NN.txt を LLM に渡し、出力を results/raw/NN.json に保存する
node report.mjs       # 照合して results/ の Markdown を書き出す
```

資料を足すときは `materials.json` に1件追加する。読む範囲を絞るときは `range` に開始と終了の見出しを書く。
