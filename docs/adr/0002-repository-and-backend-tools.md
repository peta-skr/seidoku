# ADR 0002：リポジトリの構成とバックエンドの道具

- 日付：2026年11月23日
- 状態：決定
- 関連：[フェーズ1の範囲](../phase1-scope.md)、[フェーズ1のデータモデル](../data-model.md)、[企画メモ 8章](../../portfolio-plan.md)

---

## 背景

フェーズ1の実装に入る前に、Go のバックエンドと Next.js のフロントエンドをリポジトリにどう置くかと、バックエンドで使う道具を決める。

道具を選ぶときに気にしたのは次の2つ。

- データモデルでは、別の問いの要点と結び付かないように複合 FK を使うなど、制約を DB 側で持たせている（[データモデル 4章](../data-model.md)）。この制約を、そのまま書けて、テストで確かめられること
- 面接で、SQL やテストを自分で書いたことを見せられること

## 検討した選択肢

### リポジトリの構成

- 1つのリポジトリに、`backend/` と `frontend/` を分けて置く
  - API と画面の変更を1つの PR にまとめられる
  - 見せるリポジトリが1つで済む
- Go をリポジトリの直下に置き、フロントエンドだけ `web/` に入れる
  - Go が中心のリポジトリに見える
  - 直下に Go のファイルと文書、フロントエンドの設定が混ざる
- バックエンドとフロントエンドでリポジトリを分ける
  - デプロイの単位とリポジトリが一致する
  - フェーズ1では、PR や Issue を2か所で管理する手間が増える

### Go から PostgreSQL を扱う方法

- sqlc と pgx
  - SQL を自分で書き、型付きの Go のコードを生成する
  - スキーマはマイグレーションの SQL から読むので、DB の制約をそのまま書ける
- pgx だけで書く
  - 依存は少ない
  - 行を構造体に読み込むコードを手で書くので、量が増え、列を足したときに直し漏れが出やすい
- ORM（GORM や ent）
  - SQL を書く量は減る
  - 複合 FK などの制約を ORM の書き方で表す必要があり、実際にどんな SQL が流れるかが見えにくい

### マイグレーションの道具

- goose
  - SQL のファイル1つに up と down を書く
  - Go のライブラリとしても呼べるので、テストの中でマイグレーションを当てられる
- golang-migrate
  - up と down を別のファイルに書く。利用者が多い
  - テストの中から呼ぶこともできるが、goose のほうが呼び方が簡単
- Atlas
  - あるべきスキーマを書いて差分を出す、宣言的な方式
  - フェーズ1の規模には大きい

sqlc は、どれを選んでもマイグレーションの SQL をスキーマとして読める。

### HTTP のルーティング

- 標準の `net/http`
  - Go 1.22 以降の `ServeMux` は、メソッドとパスのパラメータを扱える
  - 依存を増やさずに済む
- chi
  - `net/http` と同じ形のまま、ミドルウェアやルートのグループが使える
  - フェーズ1の API の数では、標準で足りる
- Echo や Gin
  - 機能は多いが、ハンドラの形が標準から離れる

### DB を使うテストの接続先

- docker compose で立てた PostgreSQL に、テスト用の DB（`seidoku_test`）を作る
  - 速く、仕組みも単純
  - テストの前に `docker compose up -d` が要る
- testcontainers-go
  - テストのたびにコンテナを立てるので、compose の起動を忘れても動く
  - テストが遅くなり、依存も増える

## 決定

- 1つのリポジトリに、`backend/`（Go）と `frontend/`（Next.js）を分けて置く。`frontend/` は画面を作るときに足す
- DB は sqlc と pgx で扱う
- マイグレーションは goose で書く
- ルーティングは標準の `net/http` を使う
- DB を使うテストは、compose の PostgreSQL のテスト用 DB に流す

## 理由

- 1つのリポジトリにすると、API と画面をまとめて1つの PR で見せられる。`backend/` と `frontend/` に分けるのは、Go と Node の設定ファイルが直下で混ざらないようにするため
- sqlc を選んだのは、データモデルの制約を SQL のまま書けて、SQL を書いた跡もリポジトリに残るから。手で Scan を書く量も減る
- goose は、テストの中でマイグレーションを当てる呼び方が簡単なので選んだ
- フェーズ1の API の数なら、標準の `net/http` で足りる。足りなくなったら chi に移す。chi は `net/http` と同じ形なので、移すのは難しくない
- テストの DB は、速さと仕組みの単純さを優先した。CI では、GitHub Actions のサービスコンテナで同じ PostgreSQL を立てる

## 決めた設定

- Go のモジュールは `github.com/peta-skr/seidoku/backend`
- goose と sqlc は、`go.mod` の `tool` に入れ、`go tool goose` と `go tool sqlc` で呼ぶ。手元に別に入れなくてよく、版も `go.mod` で固定される
- PostgreSQL は 16 にする。データモデルの制約を確かめた版に合わせた
- compose の PostgreSQL は、ホストの 54320 番で待ち受ける。手元に入れた PostgreSQL が 5432 番を使っていることがあるため
- DB を使うテストは、テストごとに別のスキーマを作ってマイグレーションを当て、終わったら消す（`backend/internal/testdb`）。`go test ./...` はパッケージを並行に流すので、1つのスキーマを共有するとテスト同士のデータがぶつかるため

## 影響

- テストを流す前に `docker compose up -d` が要る。起動していないと、DB を使うテストは接続できないと言って失敗する
- テストのたびにマイグレーションを全部当てるので、マイグレーションが増えるとテストが遅くなる。遅くなったら、マイグレーションを当てたテンプレートの DB から複製する形に変える
